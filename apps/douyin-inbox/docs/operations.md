# 普通抖音账号与持续私信工作流

目标体验：用户转发作品给普通抖音账号，求原图解析后在同一私信会话回复。
当前提供独立浏览器、人工登录、按需截图、单次图集测试与持续私信处理队列。
已用真实会话验证转发图集的作品 ID 提取、匿名解析下载、图片与文字回传，接收方确认收到。
转发评论中的静态图片和 GIF 已验证提取与回传，接收方确认 GIF 可以播放。
持续监听已完成指定会话测试，当前使用 `--all --send` 自动接收所有可发现的一对一会话的新请求，
无需逐个添加名单；接收方已确认不加口令转发的评论媒体可以自动回传。
评论实况另有边界：部分评论卡片仅提供单帧 JPEG，且网页评论接口未返回目标评论，不能据此提取实况视频。
遇到未核实的单帧评论预览时只发送说明。保存相册后再发送的测试仅验证原生实况收发，
用户确认平台保存会带水印，因此不能作为无水印评论实况解析的替代方案。
图集作品卡片已真实验证自动识别、解析及平台送达回执。
原生苹果实况已验证通过消息的“分享”回传，接收方确认保存到 iPhone 后有 LIVE 标记且能播放。
作品图集里的实况已验证直接配成原生实况消息；接收方确认保存到 iPhone 后有 LIVE 标记，长按播放对应风景。
陌生人会话入口、普通长视频及其他评论媒体类型尚未完成真实平台验证；
不能将队列压力测试当成账号可承载推广流量的证明。

## 安装与启动

账号工具使用专用虚拟环境安装现有可选依赖，无需修改线上服务或开发环境：

```bash
export PARSE_VIDEO_ACCOUNT_DIR="$PWD/data/accounts/douyin"
python -m venv data/accounts/douyin/venv
source data/accounts/douyin/venv/bin/activate
python -m pip install -e '.[cli]' -e ./apps/douyin-inbox
python -m playwright install chromium
python -m qiuyuantu_inbox.account doctor
python -m qiuyuantu_inbox.account login --headed
```

已有系统 Chromium 时可设置 `PARSE_VIDEO_ACCOUNT_BROWSER` 指定可执行文件；工具也会自动寻找
`chromium-browser`，找不到时使用 Playwright 安装的 Chromium。
服务器无桌面时需要 Xvfb 和仅本机可访问的远程桌面；不要把浏览器调试或远程桌面端口直接开放到公网。
无桌面的临时连通性检查可省略 `--headed`，正式扫码和验证码由账号持有人在可视化窗口中完成。
默认保留 30 分钟，`--timeout 0` 持续运行，Ctrl+C 或 SIGTERM 会关闭浏览器并保存会话。

另开终端可按需截图：

```bash
python -m qiuyuantu_inbox.account snapshot
```

控制连接固定为 `127.0.0.1:9223`。新安装的账号目录默认是 `$XDG_DATA_HOME/qiuyuantu-inbox`（缺省 `~/.local/share/qiuyuantu-inbox`），
可通过 `PARSE_VIDEO_ACCOUNT_DIR` 指定；仍兼容旧的 `PARSE_VIDEO_DATA_DIR/accounts/douyin`。
本手册的服务器示例显式沿用 `data/accounts/douyin/`，保留已有会话与队列。
目录权限为 0700，命令创建文件使用 0077 umask；其中的 profile 和截图均为敏感运行时数据，不提交、不公开托管。
自定义账号目录应放在仓库外或已有忽略目录中。
账号会话与解析器的匿名浏览器隔离，不向现有解析器导出账号 Cookie。

### 从仓库内旧入口迁移

代码已集中至 `apps/douyin-inbox/`。在原账号虚拟环境中安装
`python -m pip install --no-deps -e ./apps/douyin-inbox`，然后使用 `python -m qiuyuantu_inbox` 和
`python -m qiuyuantu_inbox.account`，替代原先主包内的入口和散落脚本。
保留 `PARSE_VIDEO_ACCOUNT_DIR` 的原值，迁移代码不移动 profile、SQLite 队列或媒体文件。
先暂停新提交并核对在途回执，再停止队列、更新服务文件和重启；账号浏览器可以保留当前已登录进程。
当前服务器已按此方式迁移，仍为 `--all --send` 和原有原生流水线参数，未重设全局基线或待选状态。

## 服务器可视化窗口

当前服务器使用系统 Chromium、Xvfb、x11vnc 和 noVNC。Fedora 可安装：

```bash
dnf install -y xorg-x11-server-Xvfb x11vnc novnc python3-websockify
```

在仓库根目录依次启动以下临时服务。服务重启服务器后不自动启动；均与线上 Web 应用分离。

```bash
systemd-run --unit=qiuyuantu-douyin-display --collect --property=UMask=0077 \
  /usr/bin/Xvfb :93 -screen 0 1360x900x24 -nolisten tcp
systemd-run --unit=qiuyuantu-douyin-vnc --collect --property=UMask=0077 \
  --property=Requires=qiuyuantu-douyin-display.service --property=After=qiuyuantu-douyin-display.service \
  /usr/bin/x11vnc -display :93 -localhost -rfbport 5903 -nopw -forever -shared -noxdamage
systemd-run --unit=qiuyuantu-douyin-desktop --collect --property=UMask=0077 \
  --property=Requires=qiuyuantu-douyin-vnc.service --property=After=qiuyuantu-douyin-vnc.service \
  /usr/bin/websockify --web=/usr/share/novnc 127.0.0.1:6083 127.0.0.1:5903
systemd-run --unit=qiuyuantu-douyin-browser --collect --property=UMask=0077 \
  --property="WorkingDirectory=$PWD" \
  --property=Requires=qiuyuantu-douyin-display.service --property=After=qiuyuantu-douyin-display.service \
  --setenv=DISPLAY=:93 "$PWD/data/accounts/douyin/venv/bin/python" \
  -m qiuyuantu_inbox.account login --headed --timeout 0
```

在自己的电脑建立 SSH 隧道（替换服务器地址）：

```bash
ssh -N -L 6083:127.0.0.1:6083 root@服务器地址
```

然后打开 <http://127.0.0.1:6083/vnc.html?autoconnect=1&resize=scale>，在窗口中扫码或完成平台验证。
VNC 不额外设置密码，访问依赖本机监听与 SSH 身份验证；不要修改为公网监听或经公开反向代理转发。
启动后用 `ss -ltn` 确认 5903、6083、9223 均只监听 `127.0.0.1` 或 `::1`。

退出验证环境：

```bash
systemctl stop qiuyuantu-douyin-browser qiuyuantu-douyin-desktop qiuyuantu-douyin-vnc qiuyuantu-douyin-display
```

## 登录后验证

1. 账号持有人用手机扫码并确认；遇到验证码或设备验证，由本人完成。
2. 检查网页是否有普通私信入口、能否收到另一账号转发的作品及图片。
3. 检查作品卡片能否获得现有解析器可用的分享链接；用 `qiuyuantu parse --format json <链接>` 验证解析。
4. 检查同一会话能否发送可保存的图片、视频或保存入口，再实现消息处理与去重。
5. 评论素材按评论卡片单独提取，不能把收到作品等同于取得评论素材；不同卡片需要检查实际媒体类型和动画帧数。

## 评论素材实测

普通私信中的评论分享卡片有独立的评论媒体元素：
`.MessageItemCommentSharecommentCover`。它与同一卡片的作品封面
`.MessageItemCommentShareawemeCover` 不同，不能把作品封面当作评论里的图片。
元素名称包含 cover，但实际文件可以是多帧 GIF，不能仅凭 DOM 标签或扩展名判断它是静态预览。
下载时沿用完整签名地址和安全下载封装，检查文件本身的格式、尺寸、帧数与时长。

本次两个样本：

| 样本 | 实际文件 | 尺寸 | 动画 |
| --- | --- | --- | --- |
| 评论图片 | WebP | 390 × 361 | 1 帧，静态 |
| 评论动态表情包 | GIF | 180 × 106 | 105 个不同画面，合计 6.66 秒 |

静态 WebP 保留下载源文件，另生成 PNG 适配私信上传；GIF 直接回传源文件，不转成截图。
接收方确认两份素材均收到，GIF 正常播放。
发送端即便已经送达，也可能保留 `blob:` 本地预览地址；发送状态不能依赖该地址是否变成 HTTPS。
持续工作流已整合评论媒体自动识别；`reply-test` 命令仍只处理图集。
这条路径依赖用户转发具体评论，尚未证明能从任意作品链接枚举或取得所有评论素材；
静态样本是否存在更高分辨率的版本也没有证据。

## 单次图集回传测试

先用另一个账号转发图集，紧接着发送文字「求原图测试」，再运行：

```bash
python -m qiuyuantu_inbox.account reply-test --conversation '测试发送者的完整显示名称'
```

运行前停留在消息列表或已经打开指定会话；若正在查看其他人的聊天，先返回列表。
命令只操作显示名称唯一匹配的指定会话。当前会话中需要恰好一条由对方发送的测试口令；
工具通过打开其前一条作品卡片取得作品 ID，不读取或导出账号 Cookie。
解析和下载复用 `qiuyuantu` 的解析器、安全客户端与超时；运行数据单独放在账号目录的 `parse-work/`。
本命令支持 1–9 张图片、每张最多 20 MiB、合计最多 100 MiB 的图集；视频和实况配套短视频不在本命令的回传范围。
JPEG、PNG、GIF 保留文件内容，静态 WebP 转成 PNG 适配聊天上传，其他格式会在发送前停止。
发送前检查收件人和空草稿，上传确认后再等待网页中的发送状态，最后发送说明文字。
私信平台可能压缩图片，接收成功不等于原始分辨率得到保留。

同一账号同时只允许一个测试命令运行，同一收件人和作品的记录放在 `test-runs/` 下。
发送前先记录 `prepared`，图片确认发出后记录 `images_sent`，文字发出后记录 `sent`。
只要已有记录，重复执行就返回 `already_recorded`，即使上次超时也不自动重发。
`prepared` 和 `images_sent` 表示需要人工核对收件端，不能当作完整成功。
此去重按显示名称和作品识别；更换显示名称会得到不同记录，不应借此重试未确认的发送。
这是手动触发的单次测试命令，没有启动后台自动回复。

`login`、`doctor` 和 `snapshot` 不发送私信；`reply-test` 与持续工作流的 `run --send` 会发送私信。
运行环境检查通过不代表平台解析或私信回传通过。
普通账号自动化没有稳定的官方接入契约，界面、登录和平台限制需要实际验证。

## 持续工作流

激活账号专用虚拟环境，先在网页打开目标会话，再启动指定会话试运行：

```bash
python -m qiuyuantu_inbox run --pilot-current --send
```

第一次保存当前会话的稳定 ID，重启沿用该 ID；昵称不参与路由。
只有启动基线之后的新请求入队，历史聊天不会触发回传。

试运行名单可以保存多个已经核对的稳定会话 ID，默认不会自动接收其他账号。
新增试运行会话设置独立的 `start_at:<会话 ID>` 基线，过滤该会话的历史请求和旧指令；
不重设全局基线，不影响原会话的待选任务。补处理遗漏的新请求时先核对原消息、发送者和会话，
仅从已确认请求的创建时间开始接收。名单和各会话基线均持久化，重启继续生效。
用户直接转发图集、视频作品卡片、具体评论媒体或抖音分享链接即可，
不需要发送口令。评论媒体直接下载；作品卡片优先复用当前客户端已加载的作品媒体地址，未命中则交给现有匿名解析器。
快路径核对原始服务端消息、发送者、会话与作品 ID，仅读取公开图片 / 视频地址，不导出整个详情载荷；
不完整图集、缺失实况视频或异常域名退回匿名解析。图片仅从无水印的 `url_list` 选择，禁止使用带用户名水印的 `download_url_list`。
首次快路径准备失败后，后续准备尝试走匿名解析，避免反复复用过期地址。普通分享链接仍使用匿名解析器。
启用发送时，匿名解析浏览器在后台预热，不阻塞收件；停机时取消预热并回收浏览器。
GIF 保留源文件，静态 WebP
保留源文件并生成上传用 PNG；回传素材不保证比平台提供的源文件更高清。
原生实况消息依据独立的 `live_photo_video.vid` 与图片摘要识别，经分享窗口原样回传；
窗口中的稳定会话 ID 必须唯一匹配，回执必须同时匹配图片摘要和实况视频 ID。
不会将图片单独下载重传后称为原生实况。无法加载源消息或确认收件人时暂停核对。
直接收到的普通照片也经原生分享回传，避免把平台加密的原始资源当作普通图片下载解码；
这与从评论卡片提取公开图片地址的路径不同。照片回执同样要求原生图片类型、新消息 ID 与图片摘要一致。

作品解析保留 `ImgInfo.live_photo_url`，缓存逐项记录照片与对应 MP4 的配对，按图集原顺序发送。
每对素材复用已登录网页实际加载的上传器和发送管理器，照片与视频并行上传，随后合成一条原生实况消息，
不先发送独立图片或视频。普通图片仍合批发送，普通视频按下述选择回传。
实况消息必须使用 `aweType: 2704`，并保留 `live_photo_video` 的独立加密视频引用；
仅向普通图片类型 `2702` 添加视频字段，接收方保存后仍为静态，已真实验证。
完整上传路径用一张 1440 × 1920 风景照片与对应 2.23 秒视频实测，接收方确认 LIVE 标记与正确动态画面。
多张实况的顺序及静态混排有离线测试，尚未完成多张实况图集的手机端验证。

发送前持久化唯一客户端消息 ID 和实况配对 ID；上传完成后再次核对账号、会话和空草稿。
回执同时匹配新服务端消息 ID、照片摘要、视频摘要、配对 ID 与原生类型；结果不确定时暂停核对。
上传凭证与媒体加密字段仅在已登录页面内使用，不返回 Python、不写日志，不导出 Cookie 或重建签名。
网页上传器的模块编号与客户端结构没有稳定公开契约，升级后无法匹配时停止发送，不能退化成静态。
卡片标记为实况却没取到视频地址时重试；配对缓存缺失时拒绝发送。准备缓存已按新版本隔离。
网页上传整体最多等待 180 秒；超时或取消后移除本次上传标记，仍在后台完成的上传不得继续提交新消息。

已上传的实况资源在页面内按账号与两个文件的 SHA-256 缓存，一小时过期，最多保留 64 对。
缓存仅保留页面内的资源引用，不保存文件字节、不写本机持久存储；刷新网页后重新上传。
命中时复用资源并生成本次任务独立的配对 ID，仍逐条落盘、核对收件人并等待新服务端回执。
不同账号、文件内容变化或过期均重新上传；缓存摘要不匹配时停止发送。

本次还测试过“原图 + 原视频 + XMP”的动态 JPG，经网页图片上传后接收方保存到 iPhone 仍为静态。
因此不能用上传 Motion Photo JPG 的成功回执证明实况保留，需同时检查消息字段与接收方保存结果。

扩大到网页一对一会话列表中可发现的所有会话时，将启动参数改为：

```bash
python -m qiuyuantu_inbox run --all --send
```

从试运行扩大范围时，原试运行会话保留独立基线，已接收任务和未应用的选择继续有效；
其他会话使用开放时的新请求基线，避免补发历史内容。独立会话基线优先于默认基线，正常重启不重设。
新用户不需要加名单；原来的试运行名单仅供缩小范围时使用，不参与 `--all` 模式过滤。
空会话不能仅凭没有 DOM 消息判定读取失败或已经完整扫描：通过客户端查询确认消息为空、没有更多历史，
且账号、会话、空草稿与最新消息状态均未变化后，才推进游标。未确认的空白保持待补扫，不暂停整个账号。
群聊不处理，陌生人消息是否进入
同一列表尚未实测。每轮最多扫描 20 屏会话、处理 10 个有变更的会话，每会话最多扫描 20 屏消息；
窗口未加载的数据不等同于已经收件。`catchup_required` 表示事件缺口、会话列表未完整扫描，
或消息扫描尚未覆盖到游标；每轮未处理完候选会话时也保留标记。
该值不证明完整覆盖所有会话入口；扩大规模前必须另测陌生人入口和多会话收件。
省略 `--send` 时只收件入队，不解析、不发送；每个账号只运行一个实例。

收件、下载准备、上传发送分开调度。浏览器操作串行；默认两个准备 worker，同一媒体的并发请求
只下载一次，跨用户复用一小时缓存。发送按实际消息数计算间隔，普通图片默认三个文件一批，按批次持久化回执。
一张实况的两个上传文件合成一条消息，因此只计一次发送间隔；普通图片批次仍按每张图计数。
每次外部发送前落盘，成功必须取得匹配会话、文件摘要和发送状态的新服务端消息 ID。
上传预览的本地地址或缺少消息 ID 不作为送达证据。
准备过程失败最多三轮、指数退避，连接建立失败先短超时并立即重试一次；永久失败发送简短反馈。
结果不确定的发送保留为 `uncertain` 并暂停，已经确认的批次不会自动重发。

### 视频与实况的回传选择

收件同时识别普通视频的类型 8 卡片与图集常用的类型 77 卡片；读取缓存详情时也核对对应类型。
解析到单条普通视频后，先发选择提示，不立即上传视频。接收方在同一私信聊天回复：

| 回复 | 回传内容 |
| --- | --- |
| `1` / `原视频` | 解析取得的视频文件，不做 GIF 转换 |
| `2` / `GIF` / `动图` | 视频前 6 秒的 GIF，短视频按实际长度 |
| `3` / `都要` | 先视频，再 GIF |

支持全角数字、键帽数字表情（例如 `2️⃣`）；不依赖平台的消息表情回应接口。
同时有多条待选择的视频时，必须附上提示中的八位编号，例如 `2 A1B2C3D4`；不猜测对应关系。
选择限同一发送者、同一会话，第一次有效选择后不可重复提交或改选。
提示取得平台回执后开始计时，默认十分钟；超时取消并发送说明，不默认发送视频。
等待状态、编号和提示回执持久保存；重启不丢选择，也不重发已确认的提示。
等待任务占用个人和全局队列配额，选择指令本身不占新的解析配额。
先核验元信息再提示，选择前不下载大文件；选择 GIF 只下载动态部分，选择 LIVE 才准备完整照片 / 视频配对。
已有完整缓存可以复用，不重复下载。等待选择不占准备 worker。
提示中的编号也支持 `进度 A1B2C3D4` 和 `取消 A1B2C3D4`，均限制同一会话、同一发送者。
准备中的取消在当前准备结束后释放资源并停止后续回传；已经开始提交的片段不能撤回。

识别完整实况配对后也先发选择提示：`1` / `LIVE` / `实况` 返回可保存的实况，`2` / `GIF` 返回动态部分的
GIF，`3` / `都要` 先发 LIVE 再发 GIF。多张实况图集只需选一次，逐项使用各自配套视频生成 GIF，
顺序与原图集一致；混排的普通图片随 LIVE 分支返回，GIF 分支仅包含实况动态部分。
作品实况的 LIVE 分支继续使用照片 / 视频配对上传，不拆成普通图片或独立视频。

相册直接发送的原生实况也支持选择。LIVE 分支继续原生分享，不下载重传；GIF 分支才请求原始视频，
核对原消息、发送者、会话、配对 ID 和图片 / 视频摘要，复用页面的请求管理器与客户端解码 worker。
该路径实测原消息的视频 MD5 对应加密媒体文件，解码后的 MP4 使用另一个缓存摘要；两者不可混淆。
只取 `original_encrypted_url`，不以转码播放资源代替；仅在页面使用资源地址及 skey / tkey。
私有进程接收大小受限的媒体字节，核对原始加密文件摘要后缓存解码后的 MP4；加密字节不落盘。
超时、取消、来源变化或摘要不符即停止准备并清理资源。原生 LIVE 回执另核对独立视频摘要。
这只是对用户实际发送素材的格式转换；来源已带水印时不会将其称为无水印原图，
也不解决缺少视频的评论卡片解析问题。

GIF 只在选择后生成，默认最长边 480、12 fps、循环播放，无音轨；超过单图大小限制后降为最长边
320、8 fps、128 色重试，仍超限则反馈失败。转换有执行超时，取消后回收编码进程与临时文件。
相同视频与相同转换参数复用 GIF 缓存；等待与回传期间同时保护原视频和 GIF 文件。
苹果实况可能使用 HEVC；需确认账号进程所用 FFmpeg 包含 HEVC 解码器。当前服务器的系统版本缺少该解码器，
账号服务已单独在 PATH 前加入私有 `bin/`，链接至账号虚拟环境中 `imageio-ffmpeg` 自带的完整版本。
该版本已把一张 720 × 904 的苹果实况视频转为 382 × 480、29 帧的 GIF；不以 MP4 容器可读取代替解码测试。
迁移环境或更新虚拟环境后，重新核对私有链接及实际解码能力，不要因此替换其他服务使用的系统 FFmpeg。
普通静态图集和原有评论 GIF 继续直接回传，不触发选择；缺少配套视频的未核实评论仍返回说明。
该入口面向作品卡片或分享链接解析到的视频，尚未适配私信相册直接发送的加密视频消息。

普通视频卡片的首次平台测试发现类型 8 未被旧适配器识别，已同时补齐收件和作品缓存读取，
并仅将原测试会话中漏掉的这一条新消息补入队列，没有重放历史聊天。
该视频已完成选择提示、接收“都要”、视频回传与 GIF 回传，三个发送片段均取得独立服务端回执。
GIF 为 270 × 480、70 帧、约 5.83 秒、4,041,518 字节；接收方确认视频和 GIF 均收到且播放正常。
单独视频、单独 GIF、多条待选与编号、重复选择、过期和恢复路径已有离线测试，
其中单独视频 / GIF 及多条待选的手机端操作尚未分别实测。

实况选择也已在一条新作品中完成提示、接收“都要”、配对 LIVE 与 GIF 回传，接收方确认可用。
多张混排及三个分支有离线测试，尚未逐一完成多张实况的手机端验证。
原生相册实况已实际取得并核对原始加密资源，解码出 589,753 字节的 HEVC MP4，转换为多帧 GIF；
它的三种选择分支及原生回执摘要校验已有离线测试，本次尚未单独完成手机端整套选择回传验证。

普通请求达到预留容量边界后不继续排队；个人超限或已知发送积压 / 受保护缓存超预算时，
同一用户最多每五分钟发送一次提示，全局容量边界时不追加提示。选择与控制消息仍受保留容量约束。
积压门槛只计算已经生成的待发片段，未完成准备的任务另受数量、文件及磁盘预算限制；不是完整排队时间预测。
这些是应用自身的资源配额，不代表抖音官方允许的吞吐量或送达时限。
SQLite 队列和发送回执位于私有账号目录 `workflow/`；终态去重元数据保留三十天，媒体缓存单独清理。
`status` 输出积压、可运行任务最老等待时长、待处理入站事件、事件 / 退化模式、补扫缺口、心跳和暂停原因，
以及最近 100 条任务的阶段平均、最大、P50 / P95 耗时：
`receive_lag`（源消息创建至本机接收，受两端时钟影响）、
`prepare_wait`（准备排队及重试退避）、`prepare`（解析下载及适配，重试累计）、
`dispatch_queue`（等待发送 worker）、`dispatch_wait`（限速及浏览器占用）、
`upload_ack`（上传至确认）、`total`（本机入队至完成）。不输出聊天原文或签名地址。
视频和实况的 `total` 包含接收方等待与回复选择的时间，不能用于衡量纯解析或转换速度。
`choice_wait` 单独记录等待选择；完成时仅记录一次 `total`，`service_total` 从中扣除已记录的选择等待。
它仍包含排队、解析与回传，不是单独的 CPU 或账号占用时间；历史任务没有新增阶段数据时不会补造。
上传另记录 `upload_select`（选择本地文件）、`upload_preview`（确认窗口）、
`upload_submit`（点击发送）、`upload_close`（窗口关闭）、`upload_delivery`（等待平台回执），
用来区分页面操作和平台传输等待。
实况另记录 `upload_native_hash`（文件指纹）、`upload_native_config`（上传配置）、
`upload_native_image` / `upload_native_video`（并行上传）、`upload_native_assets`（素材准备总耗时）、
`upload_native_submit`（消息提交）与 `upload_native_reuse`（命中已上传资源，样本数表示命中次数）。
并行阶段与总耗时存在重叠，不能相加；缓存命中不会新增图片 / 视频上传阶段的样本。

### 回传速度实测

同一张风景实况（照片 1440 × 1920、视频 2.23 秒）在本地解析下载缓存命中时：

| 回传路径 | 本次从入队到取得回执 |
| --- | --- |
| 原顺序上传 | 约 44.3 秒 |
| 图片 / 视频并行上传 | 约 10.4 秒 |
| 复用已上传资源 | 约 3.3 秒 |

接收方确认后两张均能保存为 LIVE 并正常播放。以上各为单次实际样本，网络与平台响应存在波动，
不是固定延迟承诺，也不能将全部差值归于并行上传。新作品还需额外解析下载；
并行样本中图片上传约 4.7 秒、视频约 6.7 秒，重叠后素材准备约 7.1 秒。

后续一条新的实况作品仍用时约 49 秒，其中准备约 38 秒：匿名页面首次打开失败、重试累计约 31 秒，
上传回传约 10 秒。作品卡片快路径为此减少重复导航；从已加载详情读取同一作品、重新下载并保留正确配对约 5.5 秒，
照片为 1440 × 1920；这次只测了准备阶段，未重复发送，不能当作完整收发耗时。
不能把已缓存素材约 3 秒的回传耗时用于承诺新作品的完整处理时间。

### 评论实况的已知限制

一个头发实况样本的私信评论卡片只有 `comment_url`，没有配套视频字段；
三个候选下载地址均返回同一份 1126 × 1414 单帧 JPEG，不含嵌入视频或 Motion Photo XMP。
网页显示“当前评论不可见”，按原始评论 ID 查询也未返回目标评论。
因此不能把这份预览当成 LIVE，也不能使用同作品的视频冒充评论实况。
评论详情尚未加载或无法核实、且文件只有一帧时，发送缺少视频的说明，不静默回传静态图；
已核实的静态评论和实际多帧 GIF 继续按原路径处理。

图片自身的分享入口在该样本中仍生成同一种评论卡片。接收方将原评论图片保存到 iPhone 相册，
确认 LIVE 后从私信相册发送，机器人通过原生分享约 4 秒完成回传；接收方确认仍为 LIVE、头发画面正确。
该验证只证明原生实况消息的回传；平台保存会带水印，不能作为“求原图”的交付结果。
自动回复不再引导用户先保存再发送；这种评论卡片直接解析无水印实况视频的问题仍未解决。
进一步按有限分页检查一级评论及楼中楼，并尝试客户端已有的 HEIC / WebP 格式协商，仍未匹配目标评论。
这不能证明原评论已删除，也不能把其他评论或同作品的媒体替换为目标实况。

### 多用户扩展：实现与后续验收

本节保留设计基线，并以以下状态区分已落地能力和后续验证；当前服务已从两个测试会话切换为
所有可发现的一对一会话，自动接收开放之后的新请求。

| 能力 | 当前实现与证据 |
| --- | --- |
| 事件收件与补扫 | 接入客户端管理器的 `ReceiveNewMessage` / `ReceiveSelfMessage`，只读事件不占界面锁；事件落盘后确认。真实新视频及选择回复从创建到入队分别约 1.2 / 1.3 秒，页面序号递增且已确认；单次样本不作固定延迟承诺 |
| 公平准备与发送 | 每用户最多一个准备任务；持久 DRR 按用户选择一个发送片段，普通图片每批三张，LIVE 配对保持原子性；十 / 五十 / 一百虚拟用户的轮转与守恒通过离线测试 |
| 先选择与共享计算 | 元信息先提示，选择后准备对应资源；启用原生流水线时，空闲期间预热待选的原格式（见实施记录）。共享素材和编码槽的等待状态落盘，不占 worker、不消耗重试次数；初始两个准备槽、一个编码槽 |
| 反压与控制 | 默认 280 条普通请求加 20 条控制保留容量，用户配额、已知待发预算与受保护缓存预算；支持带编号的进度 / 取消，独立控制限频 |
| 恢复与指标 | 保留发送前记录、未知送达暂停、重复事件去重及已确认片段不重发；增加事件状态、选择等待、服务总耗时与 P50 / P95 |
| 本轮真实收发 | 同一测试聊天分别发送视频与作品实况，两个编号分别选择“都要”；全部片段取得回执，接收方确认视频、两份 GIF 以及保存后的 LIVE 均正常 |
| 第二测试会话 | 新账号最初被试运行范围过滤；核对后加入名单并补处理两条新请求，图片回传及实况选择提示取得回执；随后带编号的“都要”约 0.5 秒入队，LIVE 与 GIF 均取得独立送达回执，本次最新文件的手机保存效果尚未单独确认。这是第二账号的独立验证，不代表多用户同时满载通过 |
| 待验证或后续工作 | 三至五个真实用户并发、陌生人入口、平台断网重连覆盖、多张混排实况的手机验证；上传仍持有界面锁，尚未拆成脱离会话的上传任务，回执仍沿用原生发送器 / DOM 核验 |

首次测试仅由补扫成功，不能证明事件监听有效：实际客户端管理器使用驼峰事件名，旧的连字符名称不会报错但收不到事件。
修正名称、检查客户端已有的对应监听槽后，用新消息的页面序号和入站记录确认了事件入口。
事件模式正常仅说明适配器可读，仍需结合接收延迟、序号和补扫缺口判断覆盖情况。

#### 架构选择与边界

第一阶段保留 Python、单机 SQLite WAL 和本地私有媒体缓存，在账号侧增加唯一的浏览器调度器。
解析、下载、转换由资源受限的 worker 执行；收件事件、任务、选择和发送片段全部先持久化。
浏览器及账号会话由一个进程持有，其他 worker 不直接切聊天、填写草稿或发送消息。
等待用户选择只保留数据库状态，不占 worker、浏览器锁或下载配额。

借鉴成熟队列的分组调度及持久执行思想，不在本阶段引入第二套任务状态、Redis 或 Temporal 服务。
SQLite WAL 的读写并发适合本阶段的小事务，但仍只有一个写者；事务内禁止下载、转换或浏览器等待。
多机 worker 出现实际需求或数据库写入成为可测瓶颈时，再迁移中心队列到 PostgreSQL，
媒体通过私有对象存储共享；本地 WAL 数据库不放到网络文件系统供多机共同使用。
增加媒体处理机器不会增加单个抖音账号的发送能力，扩容由实际瓶颈决定。

#### 收件：客户端事件落盘，加游标补扫

已接入并验证已登录客户端现有的接收消息事件能力；陌生人、重连等入口仍需分别实测，不能仅凭方法存在宣称全部覆盖。
事件处理器只提取白名单字段，先核对账号、会话、发送者与原始消息，分离新请求、选择指令和回执事件；
不导出客户端上下文、认证字段或媒体加密字段，也不另建平台签名请求。
不同聊天的新消息通过事件缓冲读取，避免为了收件而切换正在上传的聊天。

页面缓冲有序号和容量上限，进程取走一批后，先以数据库事务写入去重事件，再幂等应用业务待办；
事件和业务待办落盘后才确认页面序号。业务提交与事件处理标记之间崩溃时安全重放。
用户已看到选择提示但其发送回执尚未返回时，选择指令保留为延后处理的入站事件；回执核对后再应用，
不提前选择、不丢回复，也不阻塞其他入站请求。未知提示送达仍需人工核对。
去重键包含平台、机器人账号、会话和服务端消息 ID。重复事件、重启和补扫均经过同一入口。
页面刷新、网络重连、序号缺口或缓冲溢出触发补扫，缺口必须显式记录，不能静默丢弃。
没有完整扫描到持久游标时，不推进覆盖范围；“没有看到更多 DOM 节点”不能单独证明扫描完整。
陌生人入口、普通会话与重连后的事件覆盖分别验证，不能用一个测试聊天证明覆盖所有入口。

事件入口不可用时仍保留 DOM 游标扫描，且明确上报退化状态及收件延迟。
退化模式只能在浏览器操作的安全边界补扫，不承诺长上传期间即时收件。
事件只能补足在线消息，不能代替重启后的历史补扫；补扫也不能绕过仍待核对的发送状态去操作聊天。

#### 工作流：先选择，再准备大文件

视频和实况改为先解析、核验元信息，再发送选择提示；提示写“已识别”，尚未下载时不写“已解析完成”。
选择 LIVE 后下载完整照片 / 视频配对，选择 GIF 后只准备对应动态内容，选择“都要”才准备两种产物。
普通静态图片和既有 GIF 继续直接进入准备与回传。缺少配套视频的评论不能进入完整实况选择。
相册实况的 LIVE 分支维持原生分享，GIF 分支才取原始加密视频并核对摘要。
收到选择后如媒体地址已过期，按原消息、账号、发送者、会话和作品 ID 重新核验来源，不能换成其他资源。

等待选择沿用十分钟有效期、同发送者 / 同会话限制、多条必须带编号和第一次有效选择不变的规则。
增加带编号的进度和取消指令；取消只撤销尚未提交的工作，不能宣称撤回已发出的内容。
没有回复的用户不占计算资源；仅有元信息的等待任务也不长期固定大文件缓存。
已下载的共享资源按引用保护，取消一个请求不能删除其他请求仍需要的文件。

#### 公平调度：分用户、分阶段、分片段

准备阶段按用户轮转选取可运行任务，每用户初始最多一个正在准备的任务。
下载并发和 FFmpeg 并发分开：建议从两个独立媒体准备槽、一个 FFmpeg 编码槽开始，
结合 CPU、内存、下载延迟和积压再逐步调整；同素材等待者不占准备槽。

发送调度借鉴 Deficit Round Robin（DRR），以用户为分组，每次选一个有发送资格的片段，
沿用同一任务的片段顺序，发送确认后把用户放回轮转队尾，不连续占用浏览器发送整个图集。
原生 LIVE 的照片和视频仍是不可拆分的一条消息。普通图片批次初始缩为最多三张，
单个视频仍是不可抢占的原子片段；不能用轮转算法承诺一段长上传绝不影响其他用户延迟。
同一用户的独立任务可在元信息与选择阶段并行推进；已开始回传的任务保留用户内的输出顺序。
未作选择或仍在准备的任务不占据发送队首，用户不回复不能锁住后续可运行任务。

公平成本同时考虑逻辑消息数与浏览器占用时间，当前按类型的历史耗时均值预估，实际耗时用于修正后续额度；
尚未按文件体积分桶估算。
DRR 额度只决定谁先获得发送机会，不得绕过账号总发送限速；空闲用户不无限积攒额度后突发发送。
初始分组权重相同，大任务最终会获得执行机会，不采用永远让短任务插队的方式。
提示、过期及失败说明与媒体共享账号速率预算；可给控制消息保留有限份额，连续优先数量也受限，
没有控制消息时媒体可使用空余份额，防止任一类消息长期挤占另一类。

#### 浏览器：一个所有者，区分准备与提交

收件事件只读当前客户端状态；切换聊天、检查草稿、打开上传框和提交消息均由账号调度器串行执行。
能够与聊天状态无关的上传素材准备可在页面内进行，但必须先实测确认它不会修改会话、草稿或触发发送，
仍设置独立上传并发、内存与文件配额。无法确认时保持串行，不通过并开多个浏览器绕过状态约束。
需要原聊天上下文的原生媒体解码也由调度器安排，长耗时与界面临界区分别计时。

回执优先使用经过校验的客户端事件，DOM 核对作回退。只有在原生发送器及回执关联已验证、
且没有占用上传窗口或草稿时，才允许提交后释放聊天界面去做其他操作。
不确定时维持账号写入串行，事件收件与独立媒体计算仍可继续；不在尚未确认的界面状态上切换目标。
每次真正发送前仍复核稳定账号 / 会话、文件摘要、原生类型及空草稿。

#### 缓存、配额与过载

相同素材与相同参数只执行一次准备任务，其余请求登记依赖，完成后各自进入独立的发送流程。
公开媒体可在符合来源校验的范围内共用文件，私信素材及页面上传资源缓存保留账号隔离，
不能将其他账号的资源引用、密钥或发送回执拿来复用。文件字节和页面内上传资源使用不同缓存生命周期。

保留每用户三条未完成、每小时三十条、全局三百条的初始上限，等待选择仍计入未完成任务。
这些上限不是处理能力保证；接收还要同时检查积压预计服务时间、磁盘和转换资源预算。
三百个元信息任务不能等同于允许固定三百份最大媒体文件，暂存空间为下载与转换预留。
当前将全局三百条拆为 280 条普通请求与 20 条控制保留容量，个人超限提示仍限频，不产生无限回话。
同一请求的选择、取消和进度查询不作为新解析请求，但要有独立的控制指令限频。

发送继续使用账号共享的五秒间隔作为初始上限，按实际逻辑消息数计费，空闲后不补发突发额度。
遇到明确限流或服务超时，延长冷却并退避；不因服务器空闲而自动提高账号发送上限。
过载时先拒绝新增普通请求，保留已接收请求的处理和有效选择指令；排队过久时明确反馈，
不能依赖无限加长队列，也不自动将用户选的 LIVE 降为静态或 GIF。

#### 持久状态与失败恢复

复用 `jobs`、`parts`、`artifacts` 和选择记录作为事实来源；已新增 `inbound_events`、`asset_tasks`、`scheduler`、
`service_costs` 与 `command_events`，分别保存入站事件、共享依赖、调度额度、成本估计和控制限频。
每个发送片段有唯一的本地发送计划；平台支持的原生发送路径同时使用持久客户端 ID。
GUI 路径不能控制平台客户端 ID 时，不将本地去重键称为平台幂等保证。
任务状态与待发送片段在同一数据库事务提交，发送前标记尝试，发送后保存匹配的新服务端回执。

准备失败可有限重试；单个格式或资源失败只结束对应请求。
提交后超时或进程中断得到未知结果，冻结该账号的外部发送并保留人工核对入口，不盲目重发。
身份仍可确认且未被人工整体暂停时，可继续只读收件与有界准备；不能让一个不确定结果静默丢掉后续消息。
不同账号的故障分别隔离，但不以换账号补发未知结果或规避平台限制。
本方案不承诺平台未接入消息的绝对不丢失，也不宣称外部私信具备端到端 exactly-once。

#### 容量、验收和实施次序

分别记录接收发现延迟、识别、等待选择、等待计算、转换、发送排队、上传和回执延迟，
按媒体类型统计 P50 / P95、成功率、缓存命中率、补扫缺口、最老可运行片段年龄及账号利用率。
用户选择耗时不计入服务计算延迟；等待选择的积压与可运行发送积压分开。
公平轮转下不能给出一个固定不变的“前面还有 N 人”，进度反馈基于真实阶段；
有足够样本后才给宽区间估计，并解释其随平台响应变化。

以实际接收流量和每个请求消耗的平均账号服务时间评估容量，服务时间包含扫描及回传占用、
必要限速等待，不包含用户思考和后台独立计算，重叠阶段不重复相加。
初始按忙时占用约七成的内部规划目标保留余量，再以实测修正；这不是抖音允许速率或性能承诺。
持续拥堵先定位接收、计算、发送或存储瓶颈；只有独立计算拥堵才增加计算 worker。

| 顺序 | 改动位置与交付 | 验收要点 |
| --- | --- | --- |
| 1 | `browser.py` 适配只读事件批次；新增收件协调模块；`store.py` 增加入站事务 | 在线、刷新、重连、重复事件、溢出及陌生人入口分别验证；遗漏有标记 |
| 2 | 提取 `scheduler.py`；`Store.claim()` 按分组取任务；发送器一次只处理一个片段 | 大图集与短请求交错，用户内顺序正确，LIVE 配对完整；公平性不依赖真实平台压测 |
| 3 | 元信息选择与媒体准备拆阶段；共享素材任务；独立下载 / 转换配额 | 不回复不占 worker，同素材只算一次，等待者不挤满 worker，取消与缓存引用正确 |
| 4 | 拆分账号浏览器命令、上传准备与回执处理，逐条验证原生及 GUI 适配 | 任一时刻只有一个界面写入者，身份 / 草稿变化即停止；未知送达不重发 |
| 5 | 过载反馈、进度与取消、指标和运维状态 | 限额与冷却重启仍生效，磁盘不足可控，无敏感数据出现在日志或状态输出 |
| 6 | 离线混合负载、真实多会话灰度、恢复验证 | 离线至少覆盖十 / 五十 / 一百虚拟用户和三百请求上限边界；真实先用三至五个测试账号，逐步开放 |

离线测试必须注入慢下载、CPU 编码占满、共享素材失败、发送前后崩溃、回执延迟、断网重连和缓存清理。
核对请求守恒：已接收请求必须落在等待、执行、完成或明确失败等可追踪状态，不能无故消失；
检查去重、跨用户绑定、片段依赖、限速及长任务不饿死。模拟用户不能作为真实平台容量证明。
真实灰度中覆盖视频、GIF、单 / 多实况、混排及多个待选择编号；手机保存 LIVE 仍由接收方确认。
迁移时先停在可核对的发送边界，保存数据库备份并验证恢复；调度器只接管未尝试的片段，
不重放历史消息或 `uncertain`。运行范围通过明确的启动参数控制；当前已按用户要求切换为 `--all --send`，
三至五用户的同时负载与陌生人入口验证仍需分别记录，不能将开放范围视为容量验证完成。

#### 调研依据

以下资料提供模式依据，资源配额、权重、迁移时机和阶段划分是本项目的设计选择，不是资料中的性能保证：

- [Shreedhar / Varghese：Efficient Fair Queueing using Deficit Round Robin](https://repository.library.washu.edu/cse_research/339/)：按流公平分配及不可拆分服务单元的调度思想；不将网络报文公平性证明直接等同于浏览器任务延迟保证。
- [BullMQ GitHub](https://github.com/taskforcesh/bullmq) 与 [Groups 文档](https://docs.bullmq.io/bullmq-pro/groups/)：按用户分组并轮转，避免一个用户填满队列；Groups 属于 Pro 功能，本方案借鉴模式，不假设免费库已有该能力。
- [BullMQ 全局限速](https://docs.bullmq.io/guide/rate-limiting)：增加 worker 不应绕过共享限速，明确限流时让任务延后。
- [Temporal 幂等与持久执行](https://temporal.io/blog/idempotency-and-durable-execution)：恢复工作流不能自动解决外部副作用的重复执行。
- [Netflix concurrency-limits](https://github.com/Netflix/concurrency-limits)：基于延迟、积压和资源瓶颈控制并发，过载时施加反压；本项目仅将该思想用于计算和接收预算，不自动抬高平台发送上限。
- [Go singleflight 源码](https://github.com/golang/sync/blob/master/singleflight/singleflight.go)：相同键的并发执行合并；本项目需另加持久任务、取消与独立发送语义。
- [SQLite WAL 官方说明](https://www.sqlite.org/wal.html)：单机读写并发及网络文件系统限制，用于确定单机阶段和多机迁移边界。

### 账号侧上传、回执与发送节奏方案

本节保留 2026-10-26 的专项调研与选定方案。调研完成后已实施预上传、原生提交和独立回执观察，
实际启用参数、验证证据与未完成的容量验收见本节末尾的实施记录。
设计中的目标并发与算例不能当作平台容量承诺。

#### 当前瓶颈的证据

| 环节 | 当前事实 | 优化判断 |
| --- | --- | --- |
| 浏览器占用 | `Engine.send_once()` 在 `self.ui` 内等待整个 `Browser.send()`，普通媒体包含上传、发送和回执观察 | 慢文件会阻止其他人的提示和媒体提交；事件收件已经能独立运行 |
| 原生实况 | 已有照片 / 视频并行上传及页面内资源缓存；本地发送计划保留独立客户端 ID | 可沿用上传器，继续把上传与提交拆开；不应重新做一套认证请求 |
| 普通媒体 | 图片、GIF、普通视频仍走 GUI 选择文件和确认框 | 应逐种格式适配已有原生上传器 / 发送管理器，并保留 GUI 回退 |
| 回执观察 | GUI 提交后每 0.5 秒读 DOM，最长 60 秒；原生实况优先检查 SDK 结果，缺失时读 DOM | 回执改为事件关联可以减少界面占用；每轮固定等待为 0.5 秒，还应计入页面读取及调度开销 |
| 本地节奏 | 默认五秒，`next_send_at` 在调用 `Browser.send()` 前写入；一个三图批次按三条计费 | 上传和等待回执已经消耗这段时间，当前不是每次确认后再固定睡五秒 |

调研时的成功任务中，`dispatch_wait` 有 23 个任务样本，中位数为零、最大约 3.50 秒。
已有 6 个任务的 `upload_native_assets` 平均约 5.59 秒、最大 7.07 秒，包含一次资源复用；
`upload_native_submit` 平均约 1.64 秒、最大 3.04 秒。
历史 `upload_delivery` 的最大累计值约 58.24 秒，但该阶段也包含 GUI 提交后尚未完成的实际上传，
不能将它全部归因于服务端回执延迟。现有 `timings` 按任务累加，同一任务可有提示、LIVE 和 GIF 多个片段；
这些汇总不是逐条消息延迟分布，也不用于计算某个格式的 P95 或推断平台上限。

只读检查当前登录客户端得到三个进一步的适配依据：

- 已加载上传器的 `uploadImage(file)` / `uploadVideo({mp4, thumbBlob})` 接收文件和上传配置，
  方法定义中不依赖当前聊天或草稿；GIF 使用独立的图片原生类型。说明预上传值得做隔离实验，尚不能代替切换聊天时的实际验证。
- `sendMessageManager.sendMessage(builder)` 包含构建、发送前钩子、SDK 提交及成功 / 失败钩子；
  当前源码还存在一次有条件的内部重试。不能把外层调用次数当作全部网络发送次数，不能再叠加无条件应用层重试。
- 客户端已有 `MessageSendSuccess`、`MessageSendFailed`、`MessageChange`、`ReceiveSelfMessage` 事件槽。
  它们与先前接入的接收事件一样，仍需用真实原始消息核对字段和覆盖范围，不能只凭方法名宣布回执桥接已成功。

| [AWS 幂等重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)与[退避实践](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) | 未知副作用不能靠重试消除；重试会放大过载，需有预算和退避 | 原生客户端 ID 持久化，保留未知结果暂停；上传、查询和提交使用不同重试规则 |

对照源码见固定版本的 [上传与发送封装](https://github.com/Rockedw/douyin-web-api-sdk/blob/2c9d76d595717b5a186527586d3f91b6c26dc541/src/main/java/com/dy_web_api/sdk/message/DouyinMessageSDK.java)
和[发送核心](https://github.com/Rockedw/douyin-web-api-sdk/blob/2c9d76d595717b5a186527586d3f91b6c26dc541/src/main/java/com/dy_web_api/sdk/message/handler/MessageSender.java)。
调研没有运行第三方 SDK，没有把当前账号的 Cookie、认证字段或媒体密钥提供给该项目。

本次检索没有找到可直接套用、同时覆盖本项目原生 LIVE、GIF、普通视频和持久回执核验的完整实现，
因此采用上述模式，在已有登录客户端上适配。这个结论只限本次检索和已读源码，不代表不存在其他实现。
官方[企业私信接口](https://open.douyin.com/platform/resource/docs/openapi/enterprise-open-ability/message-management-enterprise/message-to-user/)
明确要求企业号授权，其发送条件不能当作普通账号的频率额度；本次没有查到可据以取消普通账号限速的公开频率承诺。

#### 选定方案：预上传、串行提交、独立回执

```mermaid
flowchart LR
  A[用户选择后准备媒体] --> B[有界上传队列]
  B --> C[页面内资源缓存]
  C --> D[按用户公平选择待发消息]
  D --> E[账号节奏器与短提交临界区]
  E --> F[有界在途回执窗口]
  F --> G[校验并持久化回执]
  G --> H[释放同任务下一条]
```

初始约束为：一个浏览器所有者、一个界面提交者、最多两个上传作业、最多两路实际文件上传，
以及总计 100 MiB 的在途文件字节预算。LIVE 的照片和视频也计入这两路上传，
不能在两份作业内各开两路而无意变成四路；视频审核封面同样受预算约束。
这些是待实验的初始值，实际浏览器内存还包含哈希、解码和复制开销，需监测后收紧。

回执窗口先保持一条，验证跨会话关联和无界面依赖后再试两条，且同一用户最多一条未确认的媒体消息。
提交入口始终串行。多个用户可以交错，单个任务仍按原顺序发送；LIVE 与 GIF 的先后以及每项照片 / 视频配对不变。
共享预上传也按用户轮转和资源成本安排，避免大图集占满全部预上传位置。

**上传阶段。** 在页面内建立独立的暂存文件入口，短暂持有界面锁完成文件交接及身份校验，
随后释放锁。上传任务只持有已绑定账号的客户端、文件与参数，不引用当前聊天、输入框或浮动上传窗口。
上传前后检查账号和页面代次，只有返回有效资源且原文件摘要匹配，才产生一个不含凭证的随机句柄。
Python 和数据库只存句柄、文件摘要、格式及过期状态；上传结果中的认证及加密资源字段留在页面内。
取消或过期的上传即使完成也不得提交消息，文件、对象 URL 和内存引用必须回收。

页面资源缓存从实况配对扩展到图片、GIF 和视频，键包含账号、文件内容摘要、原生类型及转换版本，
同键上传合并。缓存保存资源引用，释放文件字节；视频及照片可分别复用，回传 LIVE 时重新组成正确配对。
原格式保持源字节，不通过默认压缩、降分辨率或删帧提速。过期资源只在确认尚未提交时重新上传；
页面刷新导致句柄失效时，从受保护的本地文件恢复上传，不恢复或导出旧密钥。

**提交阶段。** 发送器只取资源已经齐全的消息；切换聊天、复核账号 / 会话 / 空草稿、
创建原生消息与调用发送管理器由一个调度器完成。每条平台逻辑消息有独立且持久的客户端 ID。
普通三图批次将细分为三条发送计划，各自计费和取得回执；批量预处理可以保留，不能把三条平台消息当一条限速。
GUI 回退也使用单条计划，避免一个确认框内的多条发送绕过逐条节奏约束。

客户端确认发送动作已经启动、后续只依赖不可变的 builder / conversation / message 后，
才可释放界面锁并把 Promise 结果交给回执观察器。不能仅仅把 `await sendMessage()` 删除就认为完成了解耦：
构建器、发送前后钩子、内部重试以及草稿和上传框均必须验证没有跨聊天依赖。
未通过该验证的格式继续使用原有串行路径，不混用两套提交者，也不并开多个登录浏览器。

**回执阶段。** 在提交之前安装监听并登记期待记录，防止快速回执先于等待者到达。
页面事件桥接只输出白名单字段，将客户端 ID、服务端 ID、账号、会话、原生类型、文件摘要和状态关联；
LIVE 必须同时匹配照片 / 视频摘要及原生实况类型，不能只接受通用成功事件。
去重、乱序与迟到事件通过持久状态归并；只有完整匹配才记为送达，再允许同用户的下一条媒体消息。
服务端确认不代表手机已经保存为 LIVE，手机端验证仍单独记录。

回执观察不持有界面锁。事件缺失时先用客户端缓存按已登记 ID 核对，再在安全边界做 DOM 回退；
不能为了观察回执打断另一个上传确认框或草稿。窗口满时停止新提交，上传和收件按各自预算继续。
网络与实际平台处理耗时依然存在；事件化主要减少轮询和其他用户被阻塞的时间。

#### 发送节奏的具体处理

五秒是当前应用的初始设置，本次调研不宣称它是平台规定，也不宣称改为零秒或一秒已经可用。
下一阶段将节奏器移动到**实际消息提交入口**，而不把上传开始时间当作消息提交时间：

```text
提交时刻 >= max(当前时刻, 上次实际提交时刻 + 配置间隔, 账号冷却截止时刻)
```

可采用无突发额度的虚拟时钟 / GCRA 实现。账号级预算包含提示、媒体、过期及错误反馈，
空闲后不会攒出突发额度；上传、哈希与转换可在下一发送时刻到来之前完成。
因此在保留当前配置间隔时，也能减少“到点了才开始上传”的空转，并让慢回执与其他人的准备并行。

已提交但还在等待回执的消息占用在途窗口，不能靠把窗口加大来提高配置发送频率。
出现明确的限流响应时保留平台冷却信息，并延长冷却；上传延迟和在途积压恶化时将相应并发降到一。
身份或权限异常进入暂停。重试与恢复的计时持久化，重启不会提前发，也不积攒补发额度。
将来如要降低配置间隔，应先取得适用于该账号的依据或做小范围受控验证，并记录成功率、限流和迟到回执；
本方案不自动根据短时成功率不断加速，也不把“没收到错误”当作平台允许。

客户端管理器自身的条件重试必须单独观测。未验证可控制重试行为前，外层不自动重试提交，
指标区分应用提交次数与 SDK 实际尝试次数，不能声称每个网络包都经过了外层节奏器。
能确定尚未创建任何消息的上传失败可有限重试，使用总预算和退避；可能已经发送的失败保留人工核对规则。

#### 持久状态和故障边界

复用现有 `jobs` / `parts`，增加按逻辑消息记录的上传和提交计划；不能仅在内存里维护 Promise 队列。
建议每条计划保存父任务 / 片段、序号、客户端 ID、账号 / 页面代次、摘要、资源句柄、截止时间和状态：

```text
planned -> uploading -> uploaded -> submit_intent -> submitted -> acked
                 |                        |              |
           上传重试或取消           中断需核对         未知结果需核对
```

`submit_intent` 在外部调用前落盘，中断时即使无法知道调用是否真正开始，也不能自动再发。
只有页面明确证明在调用发送器之前终止，才可退回未提交状态。上传失败不再提前标为未知送达并冻结账号。
页面句柄有账号与代次校验，上传计划可重新准备；提交计划不能因刷新页面或更换账号而重放。
多个已在途的提交分别保留回执状态，其中任何一个结果未知，都冻结该账号后续提交并核对全部在途记录。
取消停止尚未提交的计划；已经提交的消息继续跟踪回执，不能把取消等同于撤回。
缓存保护覆盖准备、预上传、待提交及等待回执的全部引用，阶段租约需续期或覆盖其完整超时预算。

#### 收益范围、实施顺序与验收

对稳定负载，单位消息间隔可用以下资源下界做规划：上传槽工作量 / 上传路数、提交临界区时间、
配置发送间隔、提交至确认的在途耗时 / 回执窗口；取其中最大的值。队列和阶段重叠需另计，不能把各阶段简单相加。
例如单个普通视频假设占用上传槽 8 秒、提交 1 秒、确认 4 秒，现有串行路径约每 13 秒推进一条；
在两路上传、五秒提交间隔、两条在途窗口都已验证的理想稳定负载下，下界约为每 5 秒一条。
这是说明流水线作用的算例，**不是抖音测速或 2.6 倍性能承诺**；首个文件仍需完成自己的上传和确认。
LIVE 应按照片加视频的总上传槽工作量计算，多张图集及“都要”还会增加实际消息数。

| 次序 | 具体改动 | 可判定的验收门槛 |

真实验证记录：预上传四种媒体期间均可切换会话，测试草稿保留且没有创建消息。
新链路的普通视频、GIF、LIVE 均获匹配回执，接收方确认视频 / GIF 正常、iPhone 保存照片有 LIVE 且可播放。
跨会话的两条文字均由事件取得回执，实际 SDK 启动间隔为 5.113 秒；两条暂未落盘确认记录可以分别归并，
发送后钩子没有清空切换后的测试草稿。随后开放账号的自动流程也完成了一条新视频的收件、选择和回传，
提示与视频各有一条事件回执，SDK 各尝试一次，没有额外重试；该视频预上传约 7.85 秒，提交至确认约 0.94 秒。
此样本不能代表慢网络下的双在途容量或 P95。

发送前钩子结束、SDK 实际提交启动后才释放 UI 锁；后续网络等待和回执观察不占该锁。
发现的客户端兼容问题已补回归：上传器加载编号独立随机生成，避免同一计划在上传重试时被模块系统去重；
SDK 实例不允许新增属性时不能静默绕过限速，无法安装提交门就停止；完整回执已证实送达但提交计数异常时，
保留已送达状态并暂停后续提交。

**选择等待期间的原格式预热。** 一条视频请求在用户选择之后，原先要依次下载（样本约 3 秒）、
预上传（约 8 秒）再提交，而用户思考期间链路空闲，已有选择又多数包含原格式。`warmup.py` 在没有正式准备或上传
排队时，每次取一条已出提示、未选择未过期的待选：把原格式下载进与正式准备相同的缓存键，以比较替换写回
`video_choices` 使其受待选保护，再通过页面上传器只传进资源缓存，不留句柄、不创建消息。选择后正式上传按账号和
文件摘要命中页面缓存，`cache_hits` 指标记录命中；预热总耗时记为 `choice_warmup`，其中下载、整段预传和上传器
实际传输分别记为 `choice_warmup_download`、`choice_warmup_upload`、`choice_warmup_stream`。相册实况的原格式是原生转发，
不预热；GIF 仍在选择后生成。代价是过期或只要 GIF 的请求白下载、白上传一次，平台侧留下未发送的上传文件。
页面刷新会丢失资源缓存，此时正式上传照常重传。
真实验证：1.9 MB 普通视频提示发出后约 2 秒开始预热，下载 2.6 秒、上传器实际传输 9.4 秒；用户约 77 秒后选择原视频，
正式上传命中缓存，从选择到取得回执约 4.4 秒。用户在预热完成前选择时，正式上传等待同一上传任务，不会重复传。
单条样本不代表 P95，上传带宽仍是图片和图集的主要耗时。

**预热与正式上传共用预算。** `upload_budget.py` 在页面接收文件前统一保留上传作业数和源字节，
包含预热与正式上传，沿用 `UPLOAD_WORKERS` / `UPLOAD_BYTES`。排队期间页面尚不持有文件；
预算满时预热直接跳过，正式请求排队，实际文件上传槽也优先放行正式请求。
例如 100 MiB 池内有 50 MiB 预热时，只能再交接一份 50 MiB 正式文件，下一份等释放后交接。
正式任务的 SQLite 认领和预取上限继续保留，页面门控制两条路径合计的实际交接量。
正在传输的文件等待当前传输结束后释放，不承诺即时抢占网络；超时、取消和 Python 所有者交接都不能提前释放。
实况使用 `allSettled` 等待照片和视频全部结束，避免其中一个失败时另一个仍在传却被当作已空闲。
同页面的预算跨进程交接保留，页面重载后重建；这限制源文件总量，不等同于浏览器进程的内存上限。

**收件和阶段主动唤醒。** SDK 事件经过 20 ms 合并后，通过页面绑定发送所有者、代次和事件序号提示，
不导出消息内容或资源凭证。Python 校验来源页面、所有者和代次后唤醒事件读取，仍坚持先落盘、后确认；
有剩余缓冲时立即继续分批读取，不因多条提示合并而每批再等一次轮询。
`wakeups.py` 用版本号覆盖“检查队列后、进入等待前”的通知，并广播给同阶段多个 worker；
收件提交后唤醒准备与计划，准备完成唤醒计划，计划完成唤醒上传，上传完成唤醒提交，提交启动唤醒回执观察。
回执落盘后立即推进后续片段，并重查早到的选择回复。通知只触发重查持久状态，不携带任务、不绕过公平调度、
账号发送间隔或未知送达核对；原有各阶段超时补查、事件轮询、60 秒会话补扫和错误退避均保留。
绑定不可用时继续轮询；缓冲溢出或代次出现缺口时也主动安排补扫。

### 运维

```bash
python -m qiuyuantu_inbox status
python -m qiuyuantu_inbox jobs --state uncertain
python -m qiuyuantu_inbox jobs --state waiting
python -m qiuyuantu_inbox pause
python -m qiuyuantu_inbox resolve <任务编号> delivered
python -m qiuyuantu_inbox resume
```

只有在收件方或平台回执证明确实收到后才用 `delivered`；确认放弃可用 `abandon`。
恢复之前处理好登录、草稿或页面异常；单纯重启不会清除暂停，也不会重发 `uncertain`。
网页截图不包含 Chromium 原生确认框；网页点击无响应时，先通过远程桌面检查是否有
“打开外部应用”等弹窗。取消外部应用启动，再核对收件游标和队列后恢复，不能重复提交已确认的发送。
账号验证仍由持有人完成。会话扫描只读取可见列表；重启后缺少末条消息时间的会话也会轮询，避免漏扫。
`pause` 阻止后续调度，已经提交平台的上传可能仍完成。后台重启恢复安全的准备任务和未尝试发送的批次。
启动基线不随正常重启变化。

`apps/douyin-inbox/deploy/` 提供固定路径的 systemd 模板，包含显示、浏览器、远程桌面与队列服务。
安装前核对工作目录、Python / Chromium 路径和 noVNC 静态目录；可选环境文件
`/etc/qiuyuantu-douyin.env` 应为 0600。默认队列仍为指定会话试运行。
开放所有一对一新请求时，安装仓库提供的独立覆盖配置；当前运行服务已启用此配置：

```bash
install -Dm644 apps/douyin-inbox/deploy/inbox-public.conf /etc/systemd/system/qiuyuantu-douyin-inbox.service.d/scope.conf
systemctl daemon-reload
systemctl restart qiuyuantu-douyin-inbox
```

覆盖配置保留账号锁、发送配额与媒体环境；移除后再重启可回到基本模板的试运行范围。
切换前在安全发送边界停止服务并备份数据库，不要通过切换模式重发未知送达的片段。
运行中的队列常驻一个 SQLite 连接，最近的提交可能还在 `queue.sqlite3-wal` 里；不停服务时用 `sqlite3 queue.sqlite3 ".backup <目标>"`，或连同 `-wal` 一起复制。
浏览器服务使用 `KillMode=mixed`，先通知主进程关闭上下文，超时后才清理子进程，减少异常退出和恢复页面提示。
先停止同名临时服务，再安装模板并启用服务；浏览器打开页面有延迟，队列会在连接失败后重启等待。

```bash
cp apps/douyin-inbox/deploy/*.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now qiuyuantu-douyin-display qiuyuantu-douyin-browser qiuyuantu-douyin-inbox
```

远程桌面仅在需要人工登录时启动 `qiuyuantu-douyin-desktop`，仍通过 SSH 隧道访问。
浏览器会话过期需要持有人重新验证；常驻进程和系统启动配置不能保证平台一直允许自动收发。
